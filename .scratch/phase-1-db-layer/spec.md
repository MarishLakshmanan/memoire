# Phase 1 — DB layer

Postgres schema for Notebook and Note (docs/adr/0001, docs/adr/0002), via SQLModel + Alembic,
running against a real Postgres in Docker rather than left unverified.

## What's here

- `docker-compose.yml` — Postgres 16 on host port **5433** (5432 is already held by an
  unrelated project's container on this machine). `docker compose up -d` to start it.
- `db/models.py` — `Notebook` and `Note` SQLModel tables. UUIDv7 primary keys (Q8: non-guessable,
  still index-friendly and time-sortable). `notebook_id` and `owner_id` both indexed.
- `db/session.py` — async engine + session factory, using SQLModel's `AsyncSession` (adds
  `.exec()`) rather than SQLAlchemy's raw one.
- `migrations/` — Alembic, async template, `DATABASE_URL` read from the environment in `env.py`.

## Verified against a real database, not just autogenerated

- Insert a Notebook + two Notes, read them back ordered by `created_at`.
- `tags` round-trips as a Postgres array.
- Deleting a Notebook cascades to its Notes — required a real fix, not just DB-level
  `ON DELETE CASCADE`: SQLAlchemy's default relationship behavior on parent delete is to
  `UPDATE` children's FK to `NULL` first, which violated `notebook_id`'s `NOT NULL` and only
  showed up by actually running the delete. Fixed with `passive_deletes=True` so the DB
  constraint is what runs.
- Migration downgrade → upgrade round-trips cleanly.
- `alembic check` reports no drift between models and the applied migration.

## Deliberately not done in phase 1

- **Ownership-enforcing query layer** (Q8: "a mandatory owner filter enforced in one shared
  query layer rather than per-endpoint"). The smoke test queried directly with a raw session
  and no owner filter — fine for proving the schema, not fine for the real tools. This has to
  land in phase 2 alongside the tool implementations, before any tool is wired to real user data.
- Full-text search (Q7) — deferred until phase 2 needs `search_notes`.
